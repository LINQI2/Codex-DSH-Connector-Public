# 01 工作流与责任

更新：2026-11-05。本页说明使用流程与交接责任，角色细则见[规则入口](../rules/README.md)，真实实现范围见[05](05-validation.md)。目标流程不代表所有步骤都已自动接通。

**连接器是增加上限的工具，不是形式化、刻板化的硬性流程。** 当前接手者在授权内负责到底。独立执行、咨询、委派都可选，按实际需要使用；不把“任务复杂”本身当作强制协作条件。

## 两种都正常的用法

- **DSH独立**：制作人/设计顾问沉淀需求 → 直接交DSH → DSH自主规划、实现、验证和收尾 → 汇报成果。无需先绑定Codex，也不强制Codex复审；Git操作仍需明确授权。
- **按需协作**：Codex接手后自行执行或委派DSH，或DSH在执行中只就具体问题咨询Codex。咨询不自动移交整包；明确委派才按约定回传与复核。

不增加模式切换表单或逐步批准。连接器的自主/确认/暂停选项控制通过连接器发送的行为，不禁止DSH在原生客户端独立完成获准任务。

## 正常研发怎样推进

| 阶段 | 谁负责 | 做什么、交给谁 |
|---|---|---|
| 讨论设计 | 制作人和GPT网页设计顾问 | 探索方案，确认后沉淀中文设计文档与执行规格 |
| 文档交接 | 制作人或明确授权代理 | 指定文档、目标、范围和授权；说明只审查还是实施 |
| 专业接手 | 实际接手者，可以是DSH或Codex | 核对工程与设计依据；需要设计一致性意见时找已有主策划/顾问 |
| 安排实施 | 实际接手者 | 自主制定适度方案，决定直接执行或确有必要的协作；不为拆包而拆包 |
| 执行与修复 | 实际执行者 | 真实修改、测试和修复；DSH能独立推进就负责到底，制作人可查看和纠偏 |
| 核验交付 | 任务接手者；必要时约定其他人复核 | 复核差异、测试及证据；不强制每项成果经过Codex |
| 产品判断 | 制作人 | 按明确要求判断设计、体验、重要取舍或指定人工验收，不逐项盲批技术日志 |

外部设计文档是主要设计入口；需要专业整合时可先交已有主策划，设计明确的实现可直接交DSH或Codex。讨论稿不自动成为权威设计，读取文档不等于授权开发。

## 遇到问题谁接手

- 普通实现、测试失败和局部修复：DSH在授权内自行处理。
- 确需额外技术判断：DSH提供事实、已试方法、问题和建议，按需咨询Codex；不强制移交。
- 设计一致性疑问：Codex对照权威设计，与已有主策划/顾问协调。
- 产品取舍、新权限、重大不可逆风险、指定人工验收或必须用户操作：直接向制作人清楚说明所需决定或动作，不只登记求助。

只暂停受影响部分，独立安全工作继续。收到明确暂停则不再派发；不能把“自主”当作扩权，也不能把每次技术失败都变成人工审批。

Git提交范围依据当前明确授权和完整依赖，不依据作者。实际接手者可独立审查与整理，获准后执行。开发完成不自动授权提交，提交也不自动授权Push。跨包混合改动需要扩大许可时，只请求准确范围，不让制作人替AI决定技术拆分方法。

## 控制方式

| 模式 | 含义 |
|---|---|
| 自主推进 | 已授权范围内自主，重要事项询问 |
| 新委派先确认 | 每个新工作包先确认，包内自主；技术答复不因此另算新工作包 |
| 暂停后续委派 | 暂停发送，保留记录；不自动停止已运行的DSH |

暂停发送、中断运行、取消询问和修改权限是不同操作，详见[08](08-session-connections.md)。程序门禁不拦截用户在原生客户端的一切直接操作。

## 当前怎样落地

明确发送用[15委派](15-planner-delegation.md)，技术回问用[09问答](09-native-routing.md)，减少轮询用[17等待](17-feedback-wait.md)。等待工具已实现且注册，原会话重载和真实长等待仍待验收；Codex回合结束后的自动唤醒未部署，不能留下“已登记所以一定有人接手”的假象。

当前一次一对绑定，尚无完整一对多调度。独立工作可在计划中判断并行条件，但不能声称连接器已能自动启动多个执行者。共享Unity工程写入、集成和冲突测试应串行。

使用现有Codex账户额度，不通过API重建规划者。网页与桌面择优，必须对应准确Session；保留现有会话和记录。当前不要求兼容旧Studio全部功能、不先建设完整自动恢复或第三方编排平台。
