# 09 技术问题路由与实际等待方

现行说明，2026-11-05。原始单次实验过程见[2026-10-31 验收](../history/2026-10-31-native-routing/ACCEPTANCE.md)，不再把已结束的调度计划写成当前待执行任务。

本页用于选择技术协作时的消息操作，不要求DSH每项任务都找Codex。独立工作能解决就自行完成；确需咨询才使用以下路径，咨询也不自动移交整个任务。

## 已有路径

DSH 官方 MCP 客户端加载 scripts/mcp.mjs 的 ask_codex，只负责具体技术提问，不提供 Shell、任意文件执行或权限修改。当前 probe profile 已有该 MCP 配置；新会话是否实际获得工具仍应核对，不能仅凭文件存在宣称调用通过。

原生工具参数必须匹配当前绑定的准确 Session、问题 ID 和内容，保存 callId/seq 后才登记。绑定暂停或断开会阻止新问题与答复，但保留已有记录。工具回复“已登记”不是 Codex 已读。

## 现在由谁处理

1. DSH 普通技术问题自行解决；需要规划者裁决时发 ask_codex，说明事实、已试方法、具体问题和建议。
2. 活动Codex可用[17反馈等待](17-feedback-wait.md)的工具监听待答问题；工具返回问题ID后通过npm run inbox读取正文并独立判断。等待不等于回答，尚未发现工具的会话不能假定自动接收已生效。
3. Codex 使用 node scripts/mailbox.mjs answer <问题ID> '<真实中文答复>' 向原 DSH 发送一次关联答复。这会触发真实 DSH 模型续接，需在任务/费用授权内。
4. 读取原生真实回复与执行结果确认续接，accepted 仅指受理。
5. Codex 不活跃且没有已部署的接收机制时，问题不会保证自动处理。必须在原生会话告诉用户“等待 Codex 读取技术问题”，不要只登记就假定维护者会处理；需用户唤起 Codex 或另行实施受支持的接收机制。

这不是每个小错误都让用户传话。只是当前缺口必须明示，不能用规则承诺伪装成已接通。重大产品取舍或新权限用原生 ask_user_question 向真人说明，不与技术裁决混为一谈。

## 记录与门禁

| 位置 | 职责 |
|---|---|
| src/mailbox.mjs | bindingId + 问题 ID、关联答复、attempt/unknown |
| src/routing.mjs | 准确原生工具来源核对、按绑定选择 Host |
| scripts/mcp.mjs | stdio MCP 提问接口 |
| .runtime/questions.json | 私有持久化收件箱 |
| .runtime/transport.jsonl | 私有实际投递记录 |

技术答复在 confirm-new 模式中不另算新工作包；新包确认不可用技术答复绕过。投递前记录稳定 requestId；unknown 先核对，不换号重发。当前 JSON 持久化尚未证明跨进程并发事务可靠，不声称完整灾难恢复。

## 已验证与未部署

2026-10-31 一次受控问题真实通过：DSH 原生提问 → 原生 heartbeat 在 Codex 上一回合结束后唤醒原聊天 → 真实答复 → 原 DSH 会话确认续接。自动化在验收后已删除，没有持续轮询。准确 ID、seq 和当时配置保留在历史报告，不能当作今天的状态。

工具内事件等待已实现且通过只读连接，长等待和真实反馈处理仍待验收；Codex回合结束后的持续接收、即时唤醒、自动成果回传和一对多完整路由未完整部署。本地脚本不能直接使用本聊天的线程工具；其他运行环境的通知接口不能不经验证套用到当前桌面对话。
