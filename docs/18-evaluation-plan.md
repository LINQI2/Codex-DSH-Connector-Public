# 18 成本、效率与质量评估模块规划

日期：2026-11-06（北京时间）。状态：已实施 E1/E2 的最小 DSH 区间账单；E3 真实新任务增长与账单对账未执行。

当前功能详见[19 使用说明](19-evaluation.md)。已支持独立统计账本、自动记录委派边界、手动登记Codex或DSH独立任务及双方协作，双方用量/运行时间/可选单价估算分开查看与导出。Codex读取本机原生指标，DSH读取官方投影；SQLite使用Node自带接口。DSH回合结束冻结区间，Codex跨回合观察直到封存，均不自动判断业务任务完成。实际金额、等待原因细分、准确率和工作方式对比未实现。下列设计中超出此范围的内容仍属后续规划。

制作人本轮调整：返修、人工介入、问题原因与经验改为 AI 简短[任务反思](../reflections/README.md)，不开发次数统计、自动归因、反思分析或评分功能。以下方案已据此收缩。

## 1. 目标与边界

让制作人看清每项工作花了多少资源、慢在哪里、是否真正完成，以及 Codex＋DSH 协作是否比独立执行更有价值。用于改进工作方法，不以单一分数评价模型。

统计不成为新的派发门槛。不强制拆包、双人协作、填写长表单或逐步人工审批；不接管原生执行框架，不复制完整聊天客户端。不新增模型调用来自动评分，不修改会话权限，不自动执行基准任务。

首版支持 DSH 独立任务和 Codex＋DSH 协作任务；保留未来其他执行者接入空间，但不先建设通用评测平台。

## 2. 已检查的基础与缺口

| 实际源码 | 已有事实 | 不能据此推定 |
|---|---|---|
| src/dispatch.mjs | 稳定发送编号、绑定与工作区、发送时间、attempted/accepted/unknown | accepted 不是开始执行或任务完成；目前没有统一任务结果账本 |
| src/client.mjs | 官方 session/list、session/page；status 可返回 tokenUsage 投影 | 未确认每个用量字段口径，也未证明可按单任务完整拆分 |
| src/feedback-wait.mjs | 官方事件流、事件序号、结束/审批等信号、一次等待耗时 | 监听耗时不是模型推理耗时；断线不是执行失败；结束不是验收通过 |
| src/mailbox.mjs | 关联问题、提问及答复尝试时间和真实状态 | 并非所有原生客户端人工沟通都经过此收件箱 |
| tests/daily-entry-real-task.mjs | 旧验证脚本曾读取 assistant/message 中 usage | 旧脚本求和方式不是已经核实的生产计费实现 |

以上是源码检查，不是本轮真实模型或账单验证。Codex 单次调用用量、原生 DSH 用量字段完整性、可核实金额均须单独验证。

## 3. 统计单位与关联

业务任务 → 多次执行尝试 → 多个原生回合/工具事件。会话可以长期复用；不能把整个会话用量直接记给某一任务。

- 连接器派发时自动建立任务关联，沿用现有发送编号，不再要求重复建任务。
- 在 DSH 原生客户端直接开始的工作，可选择已有会话和事件范围登记任务；先预览归属，不自动把所有新聊天算入任务。
- 每项任务可关联多个执行和多个会话；中途更换绑定保留原关联版本，不能回溯改写旧归属。
- 同一原生回合原则上只计入一项任务；跨任务共用的规划回合记为共享/未分摊，不重复计费。人工分摊须留依据与修订记录。
- 未归属、存在事件缺口、用量未知均单列，不以零值填充。手动补录有明确标记，不覆盖原始数据。

## 4. 指标口径

| 指标 | 首版定义 | 限制与呈现 |
|---|---|---|
| 总历时 | 任务登记起至最终验收的自然时间；未验收显示截至当前 | 历史任务无起点则未知；同时展示统计覆盖起点 |
| 执行区间 | 原生证据确认运行的时间段，单次执行区间取并集 | 包含模型与工具等待，不能称为纯推理时间；不同执行另报累计时长与并行墙钟时长 |
| 等待时间 | 仅统计原生明确起止事件能证明的等待区间 | 不开发人工补录或推测原因的分类器；缺少起止不强算，原因在任务反思解释 |
| 用量 | 分提供方/模型记录输入、输出、缓存等官方字段 | 先核实缓存是否为输入子集，禁止相加双计；原始字段与规范映射并存 |
| 费用 | 实际账单与估算费用分开展示，注明币种与来源 | 估算保存计价版本和适用日期；订阅额度无可靠归属时只报用量，金额未知，不报免费 |
| 真实验证 | 预先约定的验收项中真实通过、失败、未测、未知的数量 | 测试用例通过率与需求验收分开；模拟、分析不能冒充真实验证 |

效率不先合成一个分数。优先看每个成果的耗时/用量与客观验证结果；返修、介入及原因只在 AI 反思中简述，不做计数。首版不开发首次验收通过率或笼统准确率。费用不完整时仅对数据完整子集汇总并标明覆盖率。

## 5. 质量判断与故障归因

执行状态与成果判断分离：原生回合结束、执行尝试失败、任务交付、任务验收可以不同。执行层不能自动批准业务成果。

任务沿用已有验收要求；普通专业验证由相应负责人完成，只有确需产品判断或已指定人工验收才交制作人。统计不新增人工验收义务。

复用已有交付与验证证据，显示结果、来源和适用版本，不为评估新建评审表单或评分流程。负责人专业核验、制作人验收、仅模型自报明确区分。交付发生实质修改后，旧验证保留，不能默认沿用。

失败原因由实际接手 AI 写入任务反思，区分已确认、推测和待核对，不凭一条通用报错猜责任。不开发原因标签统计、返修或人工介入计数、自动归因。反思通常 5～10 行，一项任务一份，续接更新原文件。

## 6. 制作人界面

在连接器增加一个“评估”入口，与连接设置分开；不增加新的任务执行面板。

1. 总览：时间范围、任务数、已有交付状态、用量/费用、可核实的执行/等待时间；顶部显示数据覆盖情况。
2. 任务列表：目标、工作方式、结果、总历时、用量、最近更新时间；点击进入任务账单，不增加返修或介入列。
3. 任务账单：目标与要求 → 实际成果 → 已有验证结果 → 时间分解 → 用量；原生 ID、字段、技术事件在折叠证据中。可引用已有反思文档，不建设反思管理界面。
4. 对比在后续开放：同类任务比较独立执行与协作；同时显示样本数、任务难度/规模、工具环境、模型和规则版本。不把不同任务的观察差异宣称为因果结论。

所有金额区分“实际/估算/未知”，时间显示北京时间，存储使用 UTC。提供 CSV/JSON 导出；默认不含完整消息、凭据和原始推理内容。

## 7. 最小技术方案

复用官方只读接口和本地投递/问答记录；统计失败只影响数据完整性，不阻断开发、不重发任务。连接器运行时一个本地采集器监听已登记会话，不能为了统计唤醒 Codex。连接器未运行期间只在历史接口允许范围内补采，缺口如实标记。

建议用独立 `.runtime/evaluation/evaluation.sqlite` 保存账本，与现有绑定和投递文件分离。优先验证现有 Node 运行时自带 SQLite 接口是否适合，再定依赖；不为统计迁移原有运行数据。

最小实体：tasks（目标/工作方式/已有成果证据引用）、executions（发送与原生回合关联）、events（白名单事件摘要）、usage（原始计量及映射）、price_versions（可选计价依据）。不建 reviews 评分/归因表，不将反思解析入库。源数据记录提供方、会话、序号和来源版本。

事件以来源＋会话＋事件序号去重；用量优先按可证明的单次响应标识去重。Session 累计投影只用于核对或有条件的边界差值，不与逐回合用量重复相加。累计重置、模型切换或缺失边界时不强算。

增量游标与事件写入同事务；断线做有界重连和历史核对，不触发模型、不改变 unknown 投递状态。存储写入失败保留诊断与缺口，不悄悄标为完整。评估账本备份、导出、删除都不修改原生会话。

隐私：不采认证、完整提示词和隐藏推理；证据仅保存必要摘要/受控路径。原生公开答复按需引用，不整份复制。私有账本和真实导出默认忽略提交，测试仅使用虚构夹具。

## 8. 实施顺序与文件范围

| 阶段 | 主要工作与建议文件 | 可验收结果 |
|---|---|---|
| E1 数据账本 | 新增 src/evaluation/store.mjs、normalize.mjs、metrics.mjs，tests/evaluation-*.test.mjs；核实真实字段，必要时小改 src/client.mjs 只读投影 | 去重、用量映射、任务归属、时间并集、未知值、重启续采可测试；不接新审批 |
| E2 采集与页面 | 新增 src/evaluation/collector.mjs、API 适配及 web/evaluation 页面；按实际服务路由少量接入；原等待工具继续独立 | 原生正常工作可被观察，任务账单可读；采集器故障不影响发送/等待/客户端 |
| E3 小样本验证 | 3～5 个既有授权真实任务，记录证据并与原生客户端核对；补充导出和受限对比 | 不漏算/重复计量已覆盖事件；成本、时间与已有验证可追溯；问题原因另由 AI 简短反思 |

下一轮最小实施建议仅 E1＋E2 的单任务账单，不先开发排行榜、自动打分、全量历史扫描、通用多 Agent 调度或费用硬限额控制。详细服务接点实施前按现行源码核对，不依据本规划猜路由。

## 9. 测试与通过条件

- 单元：重复/乱序/缺失事件、累计用量重置、缓存子集、未知费用、共享回合、失败后续接、重叠执行/等待时间、修改后旧验证适用性。
- 集成：断线补采、采集器与连接器重启、账本写入失败、任务更换绑定、导出脱敏；不改变原投递防重发与权限。
- 浏览器：总览与单任务阅读、筛选、展开技术证据、空数据/不完整数据/失败反馈；不以隐藏未知值通过测试。
- 真实验收：优先观察下一次用户已授权任务，不额外制造付费调用。至少核对一次真实用量和一次执行起止；真实断线/金额对账未做则标未验证。3～5 个任务用于试用评价，不作为统计显著性证明。
- 回归：原连接选择、暂停/断开、明确委派、技术问答和等待均不受影响。类型/语法、自动化、浏览器结果分别报告。

通过标准是来源可追溯、统计口径正确、缺失可见、制作人能理解，并且没有增加工作流负担；不是必须填满四个指标。

## 10. 取舍建议与未确定项

建议直接采用：任务账单优先、被动采集、原始证据保留、专业验收复用、未知不算零、金额与用量分开、不自动模型评分。

实施时需核实：DSH 官方 usage 的计量层级/缓存/重试语义；Codex 本地可读计量是否足够且可归属；订阅或账户金额有无可信来源；原生历史补采窗口。任一来源不可用不阻塞其他指标，不伪造完整性。

目前不需要制作人判断技术细节。进入实施前只需确认按上述最小范围开展；若将来要接账单账户、上传云端、扩大读取范围或增加付费评测，再单独授权。
